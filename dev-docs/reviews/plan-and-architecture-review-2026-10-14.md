## Summary

1. **Plan: not ready to execute as written.** The amendment (line 56) is sound, but five older passages still say the rule gates block development, the status blocks show the whole critical path as blocked (with one factually false blocker), and the compensating control the amendment relies on (a release guard against unsigned profiles) has no owner, no test entry and no representation in code.
2. **Architecture: the module graph is clean and one-way today, but almost nothing is enforced by a check, and the planned RuleProfile seam is not yet data-swappable.** The base spec's decision defaults (D1–D9) are behavior, and the spec forbids options, so replacing P0 with a signed profile that differs on any decision means engine code changes.
3. **Counts: 36 findings — 0 Critical, 7 High, 22 Medium, 7 Low.** No finding blocks WI-02 from starting under P0 once F01, F03, F05 and F07 are settled.

**F06: what changes when P0-provisional is replaced by a signed profile.**

1. New profile id/version and hash; status moves from provisional to signed, with a pointer to the decision record.
2. For every D-decision whose signed answer differs from the default: a data change if decisions are profile parameters (recommended), otherwise an engine code change plus new tests.
3. Golden cases: `default-dependent` cases are re-labelled `sourced` or rewritten, in `tools/golden/build.py`, then regenerated and audited.
4. Saved development tables carry the P0 hash, so they cannot resume under the signed profile (plan line 40 principle). That is correct behavior, but it should be stated so nobody "fixes" it.
5. The signed-profile registry used by the release guard (F03) gains the new hash.

**F07.** The amendment's change-control rule ("a rule change updates the profile version, the golden cases and the affected tests") is only enforceable if the golden cases are machine-checked against the engine. Nothing connects them today. The regeneration step itself works: running `build.py` and `audit.py` into a temporary directory reproduced `golden-v1.json` and `audit-rows.md` byte-identically (139 cases, 0 FAIL, 0 consistency problems, 56 quotes checked, 0 bad).

## Architecture verdict

**Module graph (resolved with Gradle, JDK 21, offline, in a temporary copy of the repo):**

| Module | Plugin | Project dependencies | Library runtime dependencies |
|---|---|---|---|
| `:core` | kotlin-jvm + serialization plugin | none | kotlin-stdlib (serialization JSON is test-only) |
| `:session` | kotlin-jvm + serialization plugin | none | kotlin-stdlib, kotlinx-serialization-json 1.11.0 |
| `:app` | android-application, kotlin-android, compose | `:core` | Compose BOM 2025.06.01, activity-compose, core-ktx |

Direction is one-way and there are **no violations**. Two of the required directions are enforced by structure, not by intent: `:core` and `:session` are plain JVM modules, so `android.*` and Compose are not on their compile classpath; and nothing can depend on `:app`, because it is an application module. What is **not** enforced: `:core` depending on `:session` (legal in Gradle today); JDK nondeterminism APIs in `:core` (`java.util.UUID`, `java.util.Random`, `System.currentTimeMillis`); `:app` reaching into engine internals (no explicit-API mode, no `internal` discipline).

**Package layout and leaks.** One package per module, one responsibility each. Grep found no Android, Compose, `UUID`, `Random` or clock imports in `core/src` or `session/src`. The leaks are in the other direction: presentation inside `:core` (F29) and domain rules inside `:app` (F30, F31).

**Enforcement: the cheapest check for each boundary (proposed, not added).**

| Boundary | Cheapest enforceable check |
|---|---|
| `:core` has no project dependencies; `:session` depends only on `:core`; `:app` only on `:core` and `:session` | Root `build.gradle.kts`: after evaluation, iterate each project's configurations, collect `ProjectDependency` paths, and fail on anything outside an allowlist map. About 15 lines, no new dependency. |
| No `UUID`, unseeded `Random`, wall clock or `SecureRandom` in `:core` main | CI step: `git grep -nE 'java\.util\.(UUID\|Random)\|kotlin\.random\.Random\.Default\|System\.(currentTimeMillis\|nanoTime)\|SecureRandom\|Instant\.now' -- core/src/main` must find nothing. Fail if it scans zero files (same pattern as the clean-room guard). |
| No Android or Compose in `:core`/`:session` | Already enforced by the JVM plugin's classpath. Add the module allowlist above so nobody adds an Android dependency to these modules. |
| `:app` uses only the public API of `:core`/`:session` | `kotlin { explicitApi() }` in `:core` and `:session`; engine internals become `internal`. Compile error on violation. |
| Golden cases match the generator and engine | `:core` test that loads `golden-v1.json` and fails on any mismatch, plus CI `build.py` → `git diff --exit-code`. |

**Separation of concerns.** `Card.kt` mixes identity, presentation and one rule (F06, F29). `DesignPreview.kt` mixes window side effects, fixture data, a rule call and theming (F30); acceptable for a preview, wrong as a template. No file mixes domain logic with I/O yet, because no I/O exists.

**RuleProfile seam readiness.** Not ready (F06). No `RuleProfile` exists yet; that is expected. The design gap is that the decisions are specified as fixed behavior with "no options", so the seam as drafted would be a version label over code, not data. Parameterize decisions internally, hash the parameters with a specified canonical encoding (F21), and keep D10's "no user options" as a lobby rule.

**Can `:session` be written without `:app`?** Yes, if storage, crypto, clock and transport are interfaces owned by `:session` (F28), with the LAN/BLE adapters and Android storage/crypto implementations in `:app`. `:session` will need `:core` for projections and events; declare it as `api` only if `:session`'s public types expose `:core` types.

**Can `:app` avoid rule internals?** Yes, if `:core` exposes a narrow surface (profile, cards, legal actions with declarations, projections) under explicit-API mode, and `:app` obtains legal actions and previews only through that surface. Today `:app` calls `isWildcard(2)` and encodes `rank == 17` itself (F30), which is exactly the pattern to stop before WI-08.

## Recommended module layout (M0 and M1a)

No new Gradle modules are needed for M0 or M1a. The three existing modules fit the plan if their insides follow these rules:

- **`:core`** (Kotlin/JVM, KMP-compatible code only). Responsibility: card identity, `RuleProfile` and its loader, classifier and legal-action generator, deal reducer, typed events, seat and spectator projections, baseline AI policy with a node budget (not a wall clock). Allowed dependencies: Kotlin stdlib, kotlinx-serialization-json. No project dependencies. Publishes `java-test-fixtures` (golden/fixture loader, deck and state builders) for other modules' tests.
- **`:session`** (Kotlin/JVM). Responsibility: handshake, admission, capabilities, grants, framing, ordering, receipts and projection digests, in-memory transport with fault injection, event log and recovery policy, diagnostics redaction. Owns the `Transport`, `DurableStore`, `Crypto` and `Clock` interfaces. Allowed dependencies: `:core`, kotlinx-serialization-json; tests may use `testFixtures(project(":core"))`.
- **`:app`** (Android). Responsibility: Compose UI, view models, the lifecycle-independent session owner, Android implementations of the `:session` interfaces (file store, JCA crypto, NSD/socket LAN transport, wake lock), and presentation mapping of cards (glyphs, colors, labels). Allowed dependencies: `:core`, `:session`, AndroidX/Compose.

Revisit only at G3 (KMP may convert `:core`/`:session` to multiplatform modules) and at WI-10 (a BLE adapter can stay in `:app` unless iPhone sharing under KMP argues otherwise).
